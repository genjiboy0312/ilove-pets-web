# 기술 선택과 문제 해결

구현된 코드와 검증 근거를 기준으로 작성했습니다. 벤치마크 수치는 측정 환경과 범위를 함께 표기합니다. 실제 서비스에 반영되지 않은 S5는 로컬 작업본으로 구분합니다.

## 1. Supabase와 Cloudflare Pages를 선택한 이유

포트폴리오에서 사진 기록·인증·권한에 집중하기 위해 정적 React 앱은 Pages, 계정·DB·비공개 파일은 Supabase로 구성했습니다. 별도 상시 서버를 운영하지 않고 PostgreSQL의 제약·트랜잭션·RLS를 사용할 수 있습니다.

이 선택은 서버 설계를 없애지 않습니다. 소유권 검사, 공개 조회 projection, 상태 전이, 예약 용량과 재시도 계약은 SQL·Edge 함수로 구현했습니다. 외부 서비스의 요금·한도와 OAuth·메일 제공자 설정에 의존하며, 사용자가 늘어나면 쿼리·인덱스·실제 비용 측정이 필요합니다. Google Cloud는 Google OAuth 클라이언트 등록에 사용하며 앱 서버를 그곳에 호스팅하는 구조는 아닙니다.

근거: [마이그레이션](../supabase/migrations/), [함수](../supabase/functions/), [환경변수 예시](../.env.example).

## 2. 기기 기록과 클라우드를 분리한 이유

로그인하지 않은 방문자도 기록할 수 있게 메타데이터는 localStorage, 사진 Blob은 IndexedDB에 저장했습니다. 계정 저장은 Supabase로 분리하고 화면에서 목적지를 명시합니다. 로그인만으로 개인 기기 자료가 서버로 올라가는 일을 피하기 위해 가져오기는 미리보기·펫 연결·명시적 확인을 거칩니다.

대신 기기 자료는 브라우저·사이트 주소마다 다르고 동기화되지 않습니다. JSON 복원은 기기 전체 교체, 클라우드 가져오기는 원본을 남기는 비공개 복사입니다. 자동 병합과 오프라인 클라우드 쓰기는 제공하지 않습니다.

근거: [기기 저장](../src/features/local/), [자료 이전](../src/features/import/), [기기 저장 검사](../tests/local-content.spec.ts), [중단·재시도 검사](../tests/notifications-import.spec.ts).

## 3. 브라우저의 계정 상태를 권한으로 신뢰하지 않는 이유

UI에서 내 자료만 보여 주더라도 요청을 직접 만들 수 있으므로 DB RLS와 변경 RPC에서 소유권을 확인합니다. 공개 프로필·글은 필요한 필드만 반환하며, 공개 사진·스토리 함수도 현재 공개 여부·관계·만료를 검사합니다. 작업 시작 시 계정과 JWT를 고정하고 계정 전환 후 이전 비동기 응답을 폐기합니다.

버킷 전체를 공개하는 대신 사진마다 접근을 검사해 공개 취소·스토리 만료의 경계를 지켰습니다. 이미 내려받은 이미지의 회수까지 보장하는 것은 아니며, 브라우저에 전달된 사진은 복제될 수 있습니다. 서비스 역할 키는 브라우저 번들에 넣지 않습니다.

근거: [클라우드 API](../src/features/cloud/cloudApi.ts), [소셜 사진 함수](../supabase/functions/social-media/), [권한 검사](../tests/server/social-media.test.mjs), [프로필·피드 검사](../tests/server/profiles.test.mjs).

## 4. 사진 업로드를 여러 단계로 나눈 이유

`용량 예약 → 브라우저 축소 → 비공개 업로드 → 서버 디코딩·변환 → 기록 연결` 순서로 처리합니다. MIME·확장자만 믿지 않고 실제 이미지 디코딩·픽셀 수·바이트를 검사합니다. 예약 용량은 업로드 중에도 계산하며 파일 삭제가 확인되기 전에는 반환하지 않습니다.

중간 실패는 고아 파일과 용량 누수로 이어질 수 있습니다. 사진 상태와 정리 큐를 두고 재시도하며, S5 작업본에서는 lease token으로 오래된 작업의 완료 응답을 거절합니다. ImageMagick WASM은 실제 디코딩·메타데이터 제거·WebP 변환에 사용합니다. 모든 이미지 포맷이나 영상 변환을 지원하는 범용 미디어 서비스는 아닙니다.

근거: [사진 처리 함수](../supabase/functions/cloud-media/), [이미지 검사](../tests/server/image-validation.test.mjs), [S5 작업 큐 검사](../tests/server/operations.test.mjs).

## 5. 실패 후 재시도를 별도로 설계한 이유

네트워크 오류가 났다고 저장 자체가 실패한 것은 아닙니다. 변경에는 버전을 전달하고 충돌을 안내하며, 자료 이전은 원본 식별자·해시·계정별 이력을 사용해 중복 생성을 방지합니다. 신고는 성공 응답 이후에만 접수 안내를 표시하고, 계정 삭제는 서버에서 최근 인증을 재검사합니다.

백업·복원은 파싱 성공 외에도 사진 디코딩·바이트 한도를 확인합니다. S5 운영 복원 도구는 암호화·무결성 검사와 별도 빈 프로젝트 제약을 두었습니다. 격리 DB 복원 검사는 통과했지만 실제 호스팅 프로젝트 재해 복구 실증은 아직 하지 않았습니다.

근거: [이전 서버 검사](../tests/server/notifications-import.test.mjs), [실패 복구 화면 검사](../tests/portfolio-readiness.spec.ts), [암호화·복원 검사](../tests/server/backup-restore.test.mjs).

## 6. 페이지 분리와 로딩 실패 복구

모든 화면을 한 JS 엔트리로 가져오던 구조에서 홈 외 경로를 `React.lazy`로 분리했습니다. `Suspense`로 로딩 상태를 표시하고 경로 오류 경계에서 홈 이동·재시도를 제공합니다. 정적 파일을 아직 받지 않은 상태에서는 오프라인 접근이 실패할 수 있으므로 무조건적인 오프라인 지원을 주장하지 않습니다.

빌드 비교와 측정 조건은 [번들 측정 기록](bundle-measurements.json)을 참고하세요. JS 엔트리 크기와 최대 청크는 초기 전체 다운로드·LCP·실물 휴대폰 성능을 대신하지 않습니다. 페이지 이동 시 추가 요청과 실패 경계가 생기는 비용도 함께 고려했습니다.

| 측정 항목              | 이전 main `4986379` | S5·포트폴리오 작업본 |
| ---------------------- | ------------------- | -------------------- |
| JS 엔트리              | 898,901 bytes       | 197,697 bytes        |
| 엔트리 gzip            | 258,643 bytes       | 62,010 bytes         |
| 최대 JS 청크           | 898,901 bytes       | 257,143 bytes        |
| 모든 경로 JS 파일 합계 | 898,901 bytes       | 928,032 bytes        |

같은 설치 의존성·공개 인증 환경값으로 이전 커밋 복사본과 현재 production 빌드를 비교했습니다. 엔트리 파일은 78.01% 작아졌지만, S5 코드 추가와 청크 분리로 모든 경로의 JS 합계는 증가했습니다. 페이지 분리만의 독립 실험이나 앱 전체가 78% 빨라졌다는 결과가 아닙니다. gzip은 Node `gzipSync` 기본 옵션이며 Vite 로그나 서버 압축 옵션과 수치가 다를 수 있습니다.

측정 재현: 이전 커밋을 별도 임시 폴더로 내보내 같은 환경으로 Vite 빌드한 뒤 `node scripts/measure-bundle.mjs BASELINE_DIST BASELINE_REF`를 실행합니다. 이 명령은 기존 빌드 파일을 읽고 JSON만 갱신하며 이전 소스의 준비·빌드는 직접 수행해야 합니다.

근거: [라우팅](../src/App.tsx), [오류 경계](../src/components/RouteBoundary.tsx), [청크 실패 브라우저 검사](../tests/operations.spec.ts).

## 7. 검증을 세 층으로 나눈 이유

Vitest·Testing Library로 상태·폼·파서, Playwright로 화면·실제 브라우저 저장·라우팅, PGlite로 PostgreSQL 제약·RLS·RPC를 검사합니다. Storage/Auth HTTP 실패는 모의 응답을 사용합니다. 이 구분 덕분에 오류와 계정 A/B·익명 경계를 반복 재현할 수 있습니다.

PGlite는 PostgreSQL 엔진 기반 격리 검사이며 호스팅 Supabase의 네트워크·관리 설정·전체 확장 환경을 재현하지 않습니다. 브라우저 모바일 에뮬레이션도 실물 기기·Safari 통과와 다릅니다. 기존 실제 서버 확인 이력과 S5 로컬 검사를 섞어 쓰지 않습니다.

## 면접에서 설명할 수 있는 순서

1. 사용자의 문제: 반려동물 기록과 선택적 공유를 연결하고 싶었습니다.
2. 데이터 경계: 기기·개인 클라우드·공개 소셜을 분리했습니다.
3. 어려웠던 부분: 업로드 중단·공개 취소·계정 전환·중복 이전·버전 충돌을 다뤘습니다.
4. 해결 근거: 상태 전이·RLS·RPC·사진 접근 검사와 반복 가능한 테스트를 제시합니다.
5. 남은 과제: SMTP·실물 모바일·S5 실제 적용·호스팅 복원·실제 커뮤니티 연결을 솔직히 설명합니다.

프로젝트에는 AI 생성 일러스트와 AI 개발 보조를 사용했습니다. 이미지 출처·프롬프트는 [에셋 문서](../assets/README.md)에 남겼습니다. 본인의 기여를 소개할 때는 직접 이해하고 설명할 수 있는 설계·코드·검증 범위를 기준으로 작성합니다.
