# S2 비공개 클라우드 기록 연결

2026-10-15 작업본. `/cloud`에 계정 전용 펫·성장 기록·비공개 사진 게시물 화면을 구현했다. My/Settings의 클라우드 계정 카드에서 이동한다. 기존 로컬 데이터는 유지하며 자동 업로드하지 않는다. 공개 Home/Explore와 서버 기록의 통합·로컬 이전은 후속 단계다.

사용자가 S2 SQL을 실행했고 2026-10-15 사진 Edge Function 배포와 실제 두 계정/익명 DB·Storage 검증을 완료했다. 펫·성장·비공개 사진 게시물 CRUD, WebP 변환·서명 조회, 다른 계정 차단, 삭제 후 실제 파일 정리·용량 회수와 세션 갱신을 확인했다. 테스트는 32×24 PNG 표본이며 다양한 휴대전화 사진과 다른 기기 화면은 추가 확인이 필요하다. 프런트엔드도 공개 Cloudflare 사이트에 반영했고, 운영 빌드 환경의 Supabase URL·publishable key 등록 후 재배포를 완료했다.

Cloudflare 배포 `bd18a35e-4ebd-442f-963a-49a94ba9d6b9`는 success로 완료됐다. 공개 주소의 Chromium 375px 검사에서 로그인 제목·이메일 입력·Google 버튼 활성화, 가로 넘침 없음과 계정 화면 복귀를 확인했다. 실제 공개 주소에서 Google 인증을 마치고 사진을 올리는 사용자 확인은 별도다. Cloudflare OAuth 토큰은 기존 Wrangler 저장소에서 메모리로만 사용했으며 Git이나 문서에 기록하지 않았다.

## 1. 추가 DB SQL

Supabase SQL Editor의 새 쿼리에 `supabase/migrations/202610150001_private_cloud.sql` 전체를 붙여넣고 실행한다. 이미 적용한 S1 파일을 다시 실행하지 않는다. 새 파일도 한 번 적용하는 마이그레이션이며 반복 실행용 SQL이 아니다.

이 SQL은 버전 충돌 검사·요청 ID 기반 중복 방지, 소유자 전용 펫/성장/게시 CRUD, 사진 검증 상태 전환과 정리 큐를 추가한다. 클라이언트가 직접 테이블을 수정하거나 사진을 ready로 바꾸는 경로는 허용하지 않는다. `cloud_version()`으로 앱이 S2 적용 여부를 확인한다.

이어서 `202610150002_conflict_http_status.sql`을 적용한다. 개발 프로젝트에는 CLI `db query --linked --project-ref ... --file ...`로 적용을 마쳤다. 이미 적용한 앞선 마이그레이션을 수정하거나 다시 실행하지 않는다. 이 추가 SQL은 앱 충돌용 `40001`을 `PT409`로 바꿔 HTTP 409를 반환한다. 실제 HTTP 검사에서 발견한 재시도 지연을 해결했으며, [Supabase의 40001 재시도 설명](https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b)과 일치한다.

SQL 적용 후 로컬 앱 `/cloud`에서 펫·성장 기록 저장이 가능하다. 사진 함수가 없거나 상태 확인에 실패하면 사진 작성 버튼을 비활성화하고 준비 중 안내를 표시한다.

## 2. 사진 함수 배포

PowerShell에서 저장소 루트로 이동해 실행한다. 2026-10-15 사용자가 Supabase CLI 로그인을 완료했다. 프로젝트의 publishable key는 배포 권한이 없으며 배포 토큰·비밀 키를 채팅이나 Git에 넣지 않는다.

```powershell
cd D:\Project\ilove-pets-web
npx supabase login
npm run publish:edge-runtime
npx supabase functions deploy cloud-media --project-ref rdpfrblrzqphhievlihq --use-api
```

`login`은 본인 브라우저에서 Supabase 계정으로 인증한다. 최초의 정적 WASM 포함 `--use-api` 배포는 413으로 실패했다. 공식 문서상 API 방식은 정적 파일을 지원하지 않고 서버 번들 한도는 5MB다. 이후 Docker 로컬 번들링을 시도했으나 `D:\Docker\wsl\disk\docker_data.vhdx` 연결이 `E_ACCESSDENIED`로 실패했다. 디스크·ACL·기존 Docker 자료는 변경하지 않았다. [WASM 배포 안내](https://supabase.com/docs/guides/functions/wasm), [함수 제한](https://supabase.com/docs/guides/functions/limits).

현재 방식은 Docker를 사용하지 않는다. `publish:edge-runtime`이 설치된 패키지의 WASM을 준비하고 같은 프로젝트의 비공개 `ilove-pets-function-runtime` 버킷에 버전·SHA-256으로 고정된 객체를 등록한다. 키는 CLI에서 메모리로만 읽고 출력/파일 저장하지 않는다. 이미 존재하는 공개 버킷은 변경하지 않고 오류로 멈춘다. 업로드 후 서버 파일의 해시를 다시 대조한다. `magick.wasm`은 Git 제외 대상이며 새 PC에서도 준비·등록 단계가 필요하다.

2026-10-15 실행 모듈 업로드·원격 해시 대조·`cloud-media --use-api` 배포를 완료했다. 실제 로그인 사용자 `status`는 200/ready, 비로그인·잘못된 JWT는 401을 반환했다. Docker 엔진 복구는 이 배포의 선행 조건이 아니다.

함수에는 JS 코드만 API 방식으로 배포한다. 로그인 검증 후 실행 모듈을 서버 권한으로 다운로드하고 정확한 15,447,097바이트·SHA-256을 검사한 후 초기화한다. 워커 내에서는 초기화 결과를 재사용하고 일시적인 다운로드 실패는 다음 요청에서 재시도한다. 실행 모듈 약 14.7MiB와 워커 최초 다운로드도 Supabase 저장/전송 사용량에 포함될 수 있으므로 무료 할당량 안에서 확인한다. 별도의 유료 호스팅 서비스는 추가하지 않는다.

프로젝트의 서버 환경 변수 `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`를 함수 내부에서만 사용한다. 프론트엔드 `.env.local`에는 기존 공개 URL/key만 사용한다. CORS 기본 허용 origin은 Pages 주소와 로컬 5173/5174다. 다른 주소는 서버 `APP_ORIGINS`에 쉼표로 구분해 정확한 origin을 설정한다.

함수는 사용자 JWT를 `auth.getUser()`로 검증하고 이메일 확인·활성 프로필을 확인한 후에만 관리자 클라이언트를 생성한다. `verify_jwt=false`는 이 명시적인 인증 처리에 맞춘 설정이며 공개 무인증 업로드를 의미하지 않는다. 요청의 owner ID는 사용하지 않는다. [함수 인증 문서](https://supabase.com/docs/guides/functions/auth), [WASM 문서](https://supabase.com/docs/guides/functions/wasm).

## 3. 사진 처리와 실패 복구

- 사용자가 고른 JPEG/PNG/WebP는 원본 5MiB 이하, 브라우저 디코딩 후 4천만 화소 이하를 받는다. 브라우저에서 긴 변 1280px WebP로 줄여 전송한다. WebP 인코딩을 지원하지 않는 브라우저의 PNG 결과도 허용한다. 원본 파일은 수정하지 않는다.
- 서버는 별도로 실제 파일을 디코딩한다. Edge 경로는 1600px·200만 화소·5MiB를 상한으로 두고 메타데이터 제거 및 단일 프레임 WebP 재인코딩을 수행한다. 서버 검증이 끝나야 ready가 되고 게시할 수 있다. 공유 PoC 함수의 기본 4096px/800만 화소와 Edge의 더 작은 상한을 구분한다.
- 업로드 시 원본과 정규화 파일이 동시에 존재할 수 있어 10MiB를 먼저 예약한다. 서버에서 업로드 크기와 실제 파일 크기를 대조하고 두 객체 쓰기가 완료된 후 실제 업로드+정규화 파일 크기로 정산한다. 계정 50MiB, 전체 800MiB, 진행 중 예약 최대 3개다.
- 준비 중 객체와 ready의 정규화 객체만 각 소유자가 읽을 수 있다. ready의 원본은 클라이언트에 제공하지 않는다. 썸네일/메타데이터에 위치 정보를 다시 기록하지 않는다.
- 사진 조회는 60초 서명 URL을 사용하고 표시 중 45초마다 갱신한다. API/함수 응답은 PWA 캐시에서 제외된다. 발급된 URL은 만료 전까지 접근 수단이므로 공유하지 않는다.
- 삭제 시 DB에서 즉시 숨기고 두 객체의 물리 삭제가 성공한 뒤에만 용량을 해제한다. 실패하면 정리 큐와 용량을 유지하며 ‘사진 정리 다시 시도’로 재시도한다. 게시에 실패한 미사용 사진은 버리기 버튼으로 정리한다.
- 처리 중 워커가 강제 종료되면 예약을 자동으로 다시 인코딩하거나 해제하지 않는다. 관리자에게서 실행 종료를 확인한 뒤 상태·객체를 대조해야 한다. 정상 예외 경로는 `fail_media`로 정리 큐에 기록한다. 자동 정리 작업과 운영 경보는 S5에 남아 있다.
- HTTP 업로드/디코딩의 실제 Edge CPU·메모리 제한과 다양한 휴대전화 사진은 배포 후 확인해야 한다. 로컬 Deno 표본 실행 결과만으로 호스팅 환경의 성공을 보장하지 않는다.

## 4. 검증 범위와 실제 확인 순서

로컬 PostgreSQL(PGlite)에서 소유권·직접 쓰기 차단·중복 요청·오래된 수정·다른 계정·pending 사진 게시 차단·관리자 전환·삭제 용량 정산을 검사했다. 서버 HTTP 처리기는 JWT 누락/불일치, CORS, 디코딩 실패·크기 축소 신고, 불완전 정리 시 용량 유지, ready 재요청을 의존성 주입으로 검사한다. 브라우저 검사는 Supabase 응답을 모의한 CRUD·새로고침·사진 조회·모바일 화면 검사이며 실제 클라우드 통합 성공과 구분한다.

실제 프로젝트 적용 이후 다음을 확인한다.

1. Google 로그인 → My → 내 클라우드 기록 → 펫 등록·이름 수정.
2. 체중/돌봄 메모 추가 → 수정 → 새로고침 후 유지. 다른 기기에서 같은 계정으로 조회.
3. 사진 게시 → 정규화된 사진 조회 → 본문 수정 → 새로고침. 게시물은 비공개다.
4. 별도 B 계정/익명에서 A의 행·원본/정규화 파일 접근 거절. 임의 pet/asset ID, 테이블 직접 쓰기, 오래된 version 거절.
5. 손상 파일·파일 크기 위조·중복 전송·만료 예약·네트워크 실패·물리 삭제 실패를 재현하고 원본 데이터와 용량이 잘못 해제되지 않는지 확인.
6. 게시물 삭제 → 사진 정리, 성장 기록 삭제 → 펫 삭제. 로그인 계정을 바꾸면 이전 화면과 서명 URL 상태가 즉시 사라지는지 확인.

클라이언트는 작업 시작 시점의 계정 JWT를 고정해 중간 계정 전환으로 다른 계정에 쓰지 않는다. 화면도 계정 ID별로 다시 만들고 늦게 끝난 이전 조회를 반영하지 않는다. 자동 동기화 대신 서버 새로고침/변경 후 재조회 방식이며 250개씩 최대 5천 개까지 읽고, 초과하면 조용히 누락시키지 않고 오류로 처리한다.

## 로컬 실행 참고

기존 `dist/icon.svg`와 manifest에 Windows 접근/잠금 오류가 발생해 정상 출력 폴더 정리가 막혔다. 소스 빌드는 `.tmp/s2-dist`에서 통과했고 해당 산출물 및 기존 dist의 비삭제 빌드로 화면을 확인했다. 기존 잠금은 해결되지 않았으므로 일반 `npm run build` 재실행 전 파일 핸들/권한을 확인해야 한다. 신규 배포 환경의 깨끗한 출력 폴더에서도 빌드를 확인한다. 번들 크기 경고는 계속 남아 있다.
